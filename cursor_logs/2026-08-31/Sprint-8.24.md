# Sprint 8.24 — Multi-Section Document Pipeline (Комбинированные отборочные)

**Дата:** 2026-08-31
**Цель:** Устранить потерю позиций при обработке комбинированных отборочных
файлов (корпусная + мягкая мебель на одном листе), реализовав
`COMPOSITE_PICKING_LIST` / `DocumentSplitter`.

## 1. Проблема

`order_kildishov_no_barcodes.xls` содержит на одном листе два независимых
поддокумента:

1. «Отборочная ведомость ОПТ Корпусная мебель» (строки 1–27, 6 позиций / 7
   мест, заказы ЦНТ-001415 и ЦНТ-001292).
2. «Отборочная ведомость ОПТ Мягкая мебель» (строки 34–46, 1 позиция → 3
   пакета / 3 места, заказ ЦНТ-001393).

Старый `DocumentTypeDetector` находил маркер `"состоит из упаковок"` (из
секции мягкой мебели) где-то в первых 250 строках и классифицировал **весь**
файл как `SOFT_FURNITURE_TRANSFER`. В результате блок корпусной мебели (6
позиций / 7 мест) полностью терялся — нарушение Zero-Loss Invariant.

## 2. Реализация

### `src/parsers/document_detector.py`
- Добавлен `DocumentType.COMPOSITE_PICKING_LIST`.
- До проверки на `SOFT_FURNITURE_TRANSFER` детектор теперь ищет в полном
  скане листа (250 строк) заголовки `CORPUS_TITLE_RE` (`отборочн\w*
  ведомост\w* ... корпусн\w*`) и `SOFT_TITLE_RE` (`... мягк\w*`). Если найдены
  **оба** — файл помечается `COMPOSITE_PICKING_LIST`.

### `src/parsers/document_splitter.py` (новый модуль)
- `SectionType` (`STANDARD` / `SOFT`), `DocumentSection` (start_row, end_row,
  title, declared_places).
- `split_document_sections(sheet)` — находит границы секций по заголовкам
  таблиц и строкам-разделителям `ИТОГО мест по отборочной ведомости N`,
  извлекая контрольное число мест на секцию.
- `_WindowedSheetView` — лёгкая обёртка `_SheetView`, транслирующая строки
  `[start_row, end_row]` исходного листа в `[1, N]`, что позволяет запускать
  **существующие** парсеры (`v7_parser`, `soft_furniture_parser`) на
  под-диапазоне листа без каких-либо изменений в их state-machine логике.
- `extract_order_reference(text)` — динамический regex `[A-ZА-ЯЁ]{2,6}-\d{3,}`
  (не хардкод конкретных кодов) для извлечения `ЦНТ-XXXXXX` из служебной
  строки блока (`order_service_line`).
- `parse_composite_order(source, filename)` — оркестрирует: сплит → парсинг
  каждой секции своим пайплайном → присвоение `customer_override` на блок
  (с carry-forward последнего найденного `Заказ:` внутри секции) →
  сквозная перенумерация `line_number` 1..N → агрегация
  `declared_places`/`checksum_mismatch`.

### `src/parsers/v7_parser.py` / `src/parsers/soft_furniture_parser.py`
- Добавлены тонкие публичные обёртки, принимающие уже открытый (в т.ч.
  windowed) `_SheetView` напрямую, без повторного открытия файла:
  `parse_v7_blocks_from_sheet`, `extract_customer_name_from_sheet`,
  `parse_soft_furniture_blocks_from_sheet`. Внутренняя state-machine логика
  не тронута.

### `src/models.py`
- `RawOrderBlock` получил два новых опциональных поля (default безопасен для
  всех существующих тестов/данных):
  - `customer_override: Optional[str]` — заказ/заказчик для конкретной строки
    комбинированного документа.
  - `is_soft_furniture: bool = False` — маршрутизация блока в pipeline
    (мимо `HybridMatcher`, как обычная мягкая мебель).

### `src/pipeline.py`
- `parse_incoming_order` маршрутизирует `COMPOSITE_PICKING_LIST` →
  `parse_composite_order`.
- `resolve_order_decisions` → `_composite_decisions`: разделяет блоки по
  `is_soft_furniture`, прогоняет корпусные через
  `HybridMatcher.match_order_decisions` (полный 4-уровневый каскад: Exact →
  FAISS → Feature Boost → LLM → Quarantine), мягкую мебель — через
  `_soft_furniture_passthrough` (`AUTO_NO_BARCODE`). Каскадная целостность
  сохранена **на уровне секции**, а не всего документа.

### `src/adapters/wms_excel_adapter.py`
- `map_row` / `_build_workbook`: колонка «Заказчик» теперь берёт
  `decision.raw_block.customer_override or customer_name` — т.е. для обычных
  документов (override всегда `None`) поведение идентично прежнему, а для
  `COMPOSITE_PICKING_LIST` каждая строка получает свой заказ.

## 4. Ключевые design-решения

1. **Windowed sheet view вместо копирования данных.** `_WindowedSheetView`
   транслирует индексы строк — существующие `_parse_blocks_state_machine` /
   `_parse_fsm` не потребовали никаких изменений, что минимизирует риск
   регрессии в уже протестированной логике 3-строчных блоков/пакетов.
2. **`customer_override` на уровне блока, а не пересборка `V7ParseResult`.**
   Позволило переиспользовать существующий контракт `WMSExcelAdapter` (по
   аналогии с уже существующим паттерном `overrides: Mapping[int, str]` для
   штрихкодов) одной строкой в `map_row`/`_build_workbook`, не трогая
   сигнатуры `export()`/`export_to_bytes()`.
3. **`is_soft_furniture` — явный флаг, а не вывод по `item_type`.** Хотя
   `item_type == "Упаковка"` тоже отличал бы пакеты, явный булев флаг честнее
   документирует намерение и не завязан на побочном соглашении форматирования.
4. **Anti-overfitting:** извлечение заказа (`ORDER_REFERENCE_RE`) и заголовков
   секций (`CORPUS_TITLE_RE`/`SOFT_TITLE_RE`) — структурные regex-паттерны, без
   единого хардкод-списка моделей/заказов.

### `app_ui.py`
- `_decisions_to_dataframe` (Streamlit-превью таблицы результатов) строила
  колонку «Заказчик» из единого аргумента `customer_name`, минуя
  `WMSExcelAdapter.map_row`. Обновлено на
  `block.customer_override or customer_name`, чтобы интерактивный предпросмотр
  в UI тоже показывал заказ построчно для `COMPOSITE_PICKING_LIST`, а не
  только финальный экспортированный Excel.

## 5. Challenges & Caveats

- Реальный файл `order_kildishov_no_barcodes.xls` кладёт номер заказа
  (`Заказ: ЦНТ-...`) в служебную строку **каждого** блока корпусной секции —
  так что per-row извлечение сработало без доп. carry-forward логики. Для
  файлов, где заказ указывается только один раз на секцию (не на каждую
  строку), в `parse_composite_order` реализован fallback: `customer_override`
  наследует последний найденный `Заказ:` в пределах секции, а если такого нет
  вовсе — общий `customer_name` секции. Эта ветка не покрыта тестом на
  реальных данных (в имеющемся файле она не активируется) — стоит добавить
  синтетический кейс в следующем спринте, если появится файл с такой
  структурой.
- Детектор `COMPOSITE_PICKING_LIST` требует **оба** заголовка
  («...Корпусная...» И «...Мягкая...») в тексте листа. Не покрыт кейс, когда
  комбинированный документ состоит из >2 секций (например, 3 подряд разных
  типа) — `split_document_sections` уже поддерживает произвольное число
  секций структурно, но заголовок-детектор в `document_detector.py`
  проверяет только "оба типа присутствуют", что не строго требует ровно 2
  секции. Явного теста на 3+ секции нет.
- FAISS-индекс (12880 позиций каталога v8) кэшируется на диске
  (`.cache_pytest` для тестов, `.cache` для CLI) — первый прогон новых тестов
  занимает ~25-30с из-за построения индекса; последующие быстрее за счёт кэша.
